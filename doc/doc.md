# Agenvoy - Documentation

Last updated: 2026-10-16

> Back to [README](../README.md)

## Prerequisites

- Go 1.25.1 or later
- macOS or Linux; on Windows, install a WSL Linux distribution first and run Agenvoy inside its WSL terminal
- At least one configured model-provider credential; Telegram and Discord require their respective bot tokens. Speech-to-text, text-to-speech and image generation each require a selected model / provider and its credential.

## Installation

### Official installer

```bash
curl -fsSL https://agenvoy.com/scripts/install.sh | bash
agen
```

### Windows (via WSL)

Open PowerShell as an administrator, then list and install a Linux distribution:

```powershell
wsl --online --list
wsl --install <distribution-name>
```

Restart, open the installed WSL distribution, then run the [official installer](#official-installer) in its terminal.

### Build from source

```bash
git clone https://github.com/pardnchiu/agenvoy.git
cd agenvoy
go build -tags fts5 -ldflags "-X github.com/pardnchiu/agenvoy/internal/runtime.CurrentVersion=dev" -o agen ./cmd/app/
./agen
```

Building from source needs a C toolchain: `mattn/go-sqlite3` (FTS5) has no pure-Go path, so `CGO_ENABLED=1` is required.

### Using Makefile

```bash
make build
agen
```

`make build` installs the binary to `/usr/local/bin/agen` (hence the `sudo` prompt) and refreshes the bundled extensions, replacing `~/.config/agenvoy/skills/.system` and `~/.config/agenvoy/tools/.system` with the contents of `extensions/`.

| Target                                  | What it does                                                                                              |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `make build`                            | Build (version is the tag at `HEAD` when `HEAD` is exactly on one, otherwise `(dev)`), install to `/usr/local/bin/agen`, refresh bundled skills/tools |
| `make app`                              | `stop` → `build` → launch the TUI                                                                         |
| `make dev`                              | `stop` → `build` → launch the TUI with `--enable-claude-code` and `page/` served from disk (`AGENVOY_PAGE_DIR`), so frontend edits need no rebuild |
| `make stop`                             | Stop the daemon                                                                                           |
| `make update`                           | Run the official updater                                                                                  |
| `make test`                             | `go test -v -count=1 ./...`                                                                               |

### Run without installing

```bash
go run ./cmd/app/
```

## Configuration

Agenvoy stores runtime data in `~/.config/agenvoy/` and keeps credentials in the operating-system keychain; do not put API keys or tokens in project files or Git.

### Common credentials

| Keychain entry                                       | Used by                                                                     |
| ---------------------------------------------------- | --------------------------------------------------------------------------- |
| `OPENAI_API_KEY`                                     | OpenAI and OpenAI audio models                                              |
| `CLAUDE_API_KEY`, `GROK_API_KEY`, `DEEPSEEK_API_KEY`, `MISTRAL_API_KEY`, `NVIDIA_API_KEY` | The matching model providers |
| `OPENROUTER_API_KEY` | OpenRouter models and OpenRouter audio models |
| `TYPESAFE_API_KEY` | TypeSafe decision models; create one in the [TypeSafe Console](https://console.typesafe.ai/keys) |
| `CLOUDFLARE_API_KEY`, `CLOUDFLARE_ACCOUNT_ID` | Cloudflare (both required; `CLOUDFLARE_GATEWAY_ID` is optional) |
| `TELEGRAM_TOKEN`, `DISCORD_TOKEN`                    | Chat-bot integrations                                                       |
| `GEMINI_API_KEY`                                     | The Gemini model provider, Gemini audio models and voice features           |
| `OLLAMA-CLOUD_API_KEY`                               | Ollama Cloud (the hyphen is part of the name)                               |
| `COMPAT_<NAME>_API_KEY`                              | Optional key for a local / custom OpenAI-compatible endpoint named `<NAME>` |

`copilot`, `codex` and `grok-oauth` take no API key; they authenticate through an OAuth login started from `/model add`. `claude-code` uses the local `claude` CLI instead and likewise needs no API key; it appears only when Agenvoy is started with `agen --enable-claude-code` (the daemon must be stopped first).

Credentials are read in order from the operating-system keychain (service `agenvoy`), `~/.config/agenvoy/.secrets` on Linux (the fallback when `secret-tool` is unavailable, mode 0600), and the environment variable of the same name; the first one found wins.

In **Config › Model**, each API-key provider card links to its key page (`Create one in the <provider> Console.`) and each OAuth card links to its subscription page (`Subscribe on the <provider> Plans page.`). Provider model lists and the image, STT and TTS model lists are cached in ToriiDB for 15 minutes. A provider's cached lists are cleared when its key is saved or its OAuth login completes or is cleared.

### Audio and image model routing

Speech-to-text (STT), text-to-speech (TTS) and image generation models are configured separately from the session, dispatcher, and summary models. In the TUI, use `/model stt`, `/model tts` or `/model image`; choose `disable` (listed first) to turn the corresponding capability off. The TUI prints `loading...` while the available STT / TTS models are fetched in parallel from configured OpenAI, Gemini and OpenRouter providers; image generation supports OpenAI, Codex, Grok, Grok OAuth, Gemini and OpenRouter, and shows `no provider with credentials` when none of them has a credential.

Since **v0.34.4**, Telegram and Discord pause only the default flow that automatically returns voice output after voice input. The local `generate_audio` tool and audio model settings remain available: you can generate audio and send the resulting file to either channel.

### Chatbot integrations

Agenvoy currently supports Telegram and Discord. Both integrations use outbound connections from the local daemon, so the host does not need to expose an inbound port or public endpoint. Configuration requires only the corresponding bot token; a new chat must then pass a verification code (valid for 5 minutes) that the daemon logs, the TUI shows, and the `admin` chat receives when one is set. Other chatbot platforms are out of scope unless they provide a meaningful security improvement.

### Runtime configuration

`~/.config/agenvoy/config.json` contains user settings and runtime limits. `limits` can only raise a ceiling: each value is the larger of the configured value and the built-in default, so a setting below the default is ignored; a missing field uses the default and is not written back to `config.json`.

| Setting                             |   Default | Description                                                                                                                                                                                                                                                                  |
| ----------------------------------- | --------: | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `limits.max_tool_iterations`        |     `256` | Maximum tool iterations per run                                                                                                                                                                                                                                              |
| `limits.agent_send_timeout_seconds` |     `600` | Model-request timeout                                                                                                                                                                                                                                                        |
| `limits.max_history_messages`       |      `16` | Recent history messages retained                                                                                                                                                                                                                                             |
| `limits.max_history_bytes`          | `4194304` | History-size ceiling                                                                                                                                                                                                                                                         |
| `reply_lang`                        |  `"auto"` | Reply language. `auto` matches the user's message; any other value is the default language, which the language the user writes in does not change; a request or skill that asks for another language gets it for the output it covers |
| `output_dir`                        |      `""` | Where files made for the user land when the request names no location: `write_result` output, plus the documents, exports and images the agent is told to place there by default. Empty means `~/Downloads`, or `~/.config/agenvoy/download` when that folder does not exist |
| `model_tag`                         |      `{}` | Per-model tier, `{"<model>": "S"\|"A"\|"B"\|"C"\|"pass"}`; see [Model tiers](#model-tiers)                                                                                                                                                                                   |
| `net_white_list`                    |      `[]` | Hosts that `http_request` may reach even when they resolve to a loopback or private address |
| `decision_model`                    |      `""` | Decision model for dispatch, watch checks and content filtering, written `typesafe@<model>` or `openrouter@<model>`; empty or `off` turns it off. See [Decision model](#decision-model) |
| `read_only_command`                 |      `[]` | Extra commands added to the built-in read-only allowlist, matched as `bin`, `bin subcommand` or `bin subcommand subcommand` (longest first); `run_command` runs them without confirmation |

`reply_lang` accepts `auto`, a code listed in `configs/jsons/reply_lang.json` (`en`, `zh-TW`, `zh-HK`, `zh-CN`, `ja`, `ko`, `es`, `fr`, `de`, `pt`, `it`, `ru`, `vi`, `th`, `id`, `ar`) or any other language name, which is passed through to the model as written. `zh-TW` and `zh-HK` are separate: Taiwan and Hong Kong Traditional Chinese differ in vocabulary and phrasing. It applies to the agent system prompt, the `/v1/chat/completions` system prompt, the generated follow-up suggestions and the session summary. Set it from **Config › System**, which applies it to the running daemon at once; editing `config.json` by hand takes effect at the next daemon start.

`output_dir` expands `~` and creates the directory when it is saved; a path that cannot be created is rejected, and one that later becomes unusable falls back to the default. **Config › System** applies it to the running daemon at once. The same tab shows the running version beside the latest release and, only when they differ, an **update** button that opens a terminal running `agen update`. Its License card links the corresponding source on GitHub. The TUI's `/config` (reply language, output dir) writes `config.json` the same way a hand edit does.

Package defaults (not currently read from `config.json`):

| Constant                   | Default | Description                                                        |
| -------------------------- | ------: | ------------------------------------------------------------------ |
| `MAX_SESSION_TASKS`        |     `3` | Concurrent tasks per session; further tasks queue rather than fail |
| `MAX_CONCURRENT_SUBAGENTS` |     `3` | Subagent legs running at once; the rest queue                      |
| `MAX_SUBAGENT_TIMEOUT_MIN` |    `30` | Subagent timeout in minutes                                        |
| `MAX_RESUME_WAIT_MIN`      |    `60` | How long a pending resume waits for answers                        |
| `MAX_CONCURRENT_TOOLS`     |     `5` | Concurrent tool calls within one model turn; the rest queue        |

```json
{
  "limits": {
    "max_tool_iterations": 512,
    "agent_send_timeout_seconds": 900
  }
}
```

Example values take effect only when they are higher than the built-in defaults.

### TUI execution modes

The runtime ships 13 model providers, Ollama Cloud included, plus `claude-code` when started with `--enable-claude-code`, and the `compat` entry for local or custom OpenAI-compatible endpoints (Ollama, LM Studio, self-hosted gateways).

`/model add` probes a local Ollama (`http://localhost:11434/v1`) and llama.cpp (`http://localhost:8080/v1`) with `GET /models`; each one that answers is appended as **Ollama Local** or **Llama.cpp Local** to the end of the **Custom** tab in `/model add` (probe timeout 500ms) and goes straight to model selection without asking for a URL or key. Those two endpoints are built in (`configs/jsons/local_compat.json`), so nothing is written for them. Other ports or hosts are added through **Local/Custom**, which records the URL under `compats` in `config.json`. Either way the model list comes from the endpoint's own `GET /models`. Endpoint models are registered as `<name>@<model>` with the endpoint name lowercased (`ollama@gemma3:4b`); the older `compat[NAME]@<model>` form is still accepted and rewritten to the new one whenever `config.json` is loaded or saved.

The compat channel carries only the request body and `Authorization: Bearer <key>`; no vendor-specific header is sent, so an endpoint that requires one is out of scope. In scope: vendors serving their own models, OpenAI-compatible NIM, and Cloudflare. opencode Go (`opencode.ai/zen/go/v1`) is excluded on that rule — since its [2026-09-03 announcement](https://x.com/opencode/status/2095410501400289576) it rejects requests without a per-conversation `x-opencode-session` header (`400 MissingSessionID`), and Chat Completions is stateless, so tracking and rotating a private header per conversation is not OpenAI-compatible behaviour.

When the input area is empty, press `Shift+F` to toggle fast mode. The header displays `[fast]` while it is enabled. Fast mode is process-local and is not persisted in `config.json`; it passes `core.ModeFast` through `go-llm-router` so supported provider backends can request a faster service tier. The default mode remains available when fast mode is disabled.

### Agent selection and confirmation routing

When a request starts with `/<skill_name>` or matches a Skill, the dispatcher receives that Skill's description as a selection hint. Scheduled Skill runs go through the subagent path, which passes the Skill body as the request without this hint, and a Skill the model loads mid-turn with `run_skill` does not re-select the model. Model selection therefore reflects the active task contract instead of relying on the user text alone. While assembling the prompt, Agenvoy adds its common official operating guide and, when configured, the guide that matches the selected model.

### Model tiers

Each registered model can carry a tier in `model_tag`:

| Tier   | Meaning                                                                                          |
| ------ | ------------------------------------------------------------------------------------------------ |
| `S`    | Strongest; code and work that asks for depth or precision                                        |
| `A`    | Default for most work, one step below the flagship                                               |
| `B`    | Mainstream mid tier                                                                              |
| `C`    | Fast and cheap; calls tools reliably as instructed                                               |
| `pass` | Never picked by auto routing, subagents or fallback, even when the request names it; used only when a session is set to it |

Set a tier with `t` on a model row in the TUI `/model`, or with the tier button on each card under **Config › Model › Fallback Priority**. Tiers are read per request, so a change applies without a restart.

A model pinned to the session skips ranking and fallback, but when the session reasoning is `auto` the selector is still called for the reasoning level. Otherwise the dispatcher receives every registered model already resolved to its tier; an untiered model is placed by its name (`claude-opus` S, `claude-sonnet` A, `claude-haiku` B, `*-mini` and open-weight models such as `gemma*` / `qwen*` C, and so on). The kind of work decides the order: code, or a request that asks outright for depth or precision, tries S first; research that gathers from several sources and synthesizes tries S; review, planning, drafting and everything else try A; greetings, short answers, chat and translation try B; fetching data with tools and returning it tries C. The LLM dispatcher, the decision model and the subagent planner read this one table and one name rule, so their rankings agree. Inside a tier, models on the subscription providers `claude-code` and then `codex` rank ahead of every other provider. When the same model is registered under several providers, the order within it is `claude-code`, then `codex` / `grok-oauth`, then `copilot`, then the direct API, then `openrouter` (an `openrouter` model name is compared with its vendor prefix stripped); a named or continued model stays at the front and only the candidates after it are reordered. `copilot` resells smaller context windows, so long inputs and `research` work prefer other providers. `pass` is enforced in the prompt and in the fallback chain: the dispatcher is told never to return a `pass` model, any `pass` name a selector returns is dropped, and fallback tries every other registered model in the priority order, `pass` excluded, skipping the failed model's provider and confirming each candidate with a health check (10 seconds); when a whole round fails it retries up to 4 rounds before failing. When a stream stops responding, a watchdog also switches to the next model. Context limits come from `llm-io.agenvoy.com`, cached for 1 hour; `copilot@` models asynchronously warm a Copilot-specific model-limit cache from the GitHub Copilot models API, refreshing at most every 24 hours; chat models use the reported `max_context_window_tokens` when available. Unknown Copilot models and other unlisted models use the general 128K input window. The TUI shows current context tokens against the resolved input window; history compaction starts at 80%.

Once it fans out, the main agent only splits the task, dispatches legs and synthesizes their results; each leg has one job — collect, analyze, compare, review, transform or code. The `subagent_dispatch` topic of `reasoning_guide` gives the main agent the same tiers one tier lower (S→A, A→B, B→C) as a reference: collect → fetch (C>B>A>S), transform → chat (C>B>A>S), analyze, compare and review → work (B>A>C>S), code or high-precision work → code (A>B>C>S); this is model-selection advice for the main agent, and the code does not enforce it. Each leg's `model` is required and checked against the live registry, so models added after startup work, and an unregistered or `pass` model is rejected. An explicitly named model overrides the model pinned to the `self_id` session; `auto` first reuses that session's pinned model, and only when there is none lets the dispatcher pick from the leg's task. `reasoning` defaults to `auto` (the session setting, decided by the selector when that is also `auto`); an invalid value returns an error listing the valid levels. At most 3 legs run at once, and reports are written to `~/.config/agenvoy/download/temp-<report_name>.md`.

### Decision model

A decision model answers typed questions — pick one option, with a confidence — in well under a second, so Agenvoy uses it to route requests and to filter what reaches the main model. Two providers serve it: `typesafe` (`TYPESAFE_API_KEY`) and `openrouter` (`OPENROUTER_API_KEY`, the models that output decisions; `cloudflare/clairic`, `respan/span-01*` and `scaledown/classify-1` are left out because they reject Agenvoy's request format). The option list is cached for 15 minutes and dropped when a provider key changes. Pick the model with `/model decision` in the TUI or the **Decision** card under **Config › Model**; it is stored as `decision_model`, and `off` (or empty) turns every use below off. A TypeSafe key is added like any other API key — `/model add` → **API Key** → **TypeSafe** in the TUI, or the TypeSafe card on the web **API Key** tab — and saving it only stores the key; the model is then picked under Decision. TypeSafe models are also kept out of OpenRouter's chat-model list.

Every call times out after 3 seconds. Apart from dispatch and the skill list, an answer acts only at a confidence of 0.7 or above, and a failed call leaves things as they would be without a decision model.

| Use | What it decides | When there is no answer |
| --- | --- | --- |
| Dispatch | Kind of work, an explicitly named model, and whether the request continues the last one; runs alongside the dispatcher model and the first valid answer wins | The dispatcher model's answer |
| Watch (`background_command`) | Whether output flagged by an error keyword shows a real failure, and whether it only repeats the last report; benign hits and repeats are not reported | The flagged output is reported unchecked, with the failure noted. Without a decision model every keyword hit is reported once output settles (2 s of quiet, at most 10 s), at most one report per 30 s, with up to 8 KiB of the latest output |
| `search_web` | Which result titles bear on the request; the rest are dropped | All results |
| `fetch_page` (markdown) | Which blocks are page chrome, removed before caching; whether the page bears on the request, otherwise it is withheld | The full page |
| Turn context | Whether any available tool covers the request, otherwise a hint points to the tool-building guide; which skills are relevant, the rest are left out of the list | No hint; the full skill list |
| Session summary | Which exchanges are noise and which `key_decisions` / `past_discussions` are outdated; both are dropped before merging | Every exchange and entry |
| Context overflow | Which tool steps the request no longer needs, dropped before oldest-first trimming; the latest step and `write_todo` are always kept | Oldest-first trimming only |

Dispatch through the decision model is on whenever `decision_model` is set; it runs alongside the dispatcher model and the first valid answer wins. For dispatch the decision model receives the request and up to four recent user/assistant messages, each cut at 2,048 characters. It classifies the request into one kind of work, which sets both the model order and the reasoning level. A second question catches an explicit "use / with <model>" request among the non-`pass` models and puts that model first. When the session's previous model is still a candidate, a third question asks whether the request continues the last user message; if it does, that model goes right after any named model, and unless a different model was named, the reasoning level reuses the previous one (replacing this request's classification). The previous model is recorded after each successful reply under `lastModel:<session>` in ToriiDB db_0 and expires after 30 minutes for `openai` / `codex`, 60 minutes for `gemini`, and 5 minutes for other providers.

| Work | Covers | Tier order | Reasoning |
| --- | --- | --- | --- |
| `code` | Writing, fixing, debugging or testing code; requests that ask outright for depth or precision | S>A>B>C | `xhigh` |
| `chat` | Greetings, short answers, translation | B>C>A>S | `none` |
| `fetch` | Fetching data with tools and returning it without judgement | C>B>A>S | `low` |
| `research` | Gathering from several sources and drawing conclusions: research, analysis, comparison, reports | S>A>B>C | `high` |
| `work` | Planning, review, drafting or organizing content the user already has, and anything else | A>S>B>C | `medium` |

Tiers come from `model_tag`, then from the model name for untiered models. `pass` models are left out of this ranking and out of the fallback chain, and a request naming one does not select it; they run only when a session is set to one. The default dispatcher prompt uses the same five kinds and tier orders: it answers with the work kind on its first line and the model names on the second, so the reasoning level in the table above is available without a decision model. Three things are decided separately: **which selector runs** (a decision model set → the decision model alongside the dispatcher model, otherwise the dispatcher model alone), **which model is used** (the selector's order only when the session model is `auto`; a pinned model is kept), and **which reasoning level is used** (the selector's level only when the session reasoning is `auto`, falling back to `medium` when the selector returned none; any other session level is kept). A level passed with the request (for example `reasoning_effort`) still wins over both. New sessions (`temp-` included) default to `medium` reasoning; set it to `auto` to use the selector's level.

Reply footers in the TUI, web, Telegram and Discord show the level actually used as `model/reasoning`. The `done` line in `action.log` records it as `reasoning=<level>`, so the web chat still shows it after a reload. The web reasoning trace opens with `Model(<model> <level>)` and adds `Switch(...)` when a later turn changes model; once a turn has completed, a reload drops these lines.

Interactive requests also carry an origin prefix. CLI confirmations are consumed only by the TUI, web requests by the web confirmation stream, and Telegram or Discord requests by their matching channel listeners. Non-TUI confirmations expire after five minutes; the task is then cancelled and kept as pending so it can be resumed later, preventing one channel from intercepting or indefinitely holding another channel's prompt.

### Restricted paths and commands

Paths outside `$HOME` and paths on the sensitive list (`configs/jsons/sensitive_path.json`, extendable through `sensitive_path` in `config.json`) are not refused outright: `boundary.Restricted` collects them and raises a confirmation that also demands the operating-system password (a password field in the TUI or web confirmation, verified by the daemon). `run_command` and `background_command` calls with argv `['sudo', ...]` or `sandbox: false` are gated the same way in every permission mode; once verified, `sudo` runs as `sudo -n` on the ticket that verification left. In the TUI, a `!` shell command containing `sudo` asks for the password in a popup first when no sudo ticket is valid. Approval is bound to that session and the specific path and lasts for the life of the daemon; whether the password field appears follows the sudo timestamp (`sudo -n -v`): while that ticket is still valid the prompt appears without a password field. `denied_path` and `denied_command` in `config.json` are hard rejects that no approval can lift; any command not on `denied_command` runs, subject to the normal `run_command` confirmation.

Two consequences worth knowing before automating anything:

- Normal tool confirmations return to the originating CLI, web, Telegram, or Discord channel. The TUI listens only for CLI-origin requests.
- Restricted operations that require operating-system verification still execute only when that verification is available. A channel may approve the prompt, but an unverified restricted call is skipped rather than elevated.
- The `run_command` sandbox constrains writes, not reads, so a command fails on a path only when the operating system itself refuses; the file tools (`read_files`, `find_files`, `open_file`, `file_history`) still ask for confirmation to read outside `$HOME` or a sensitive path, and `denied_path` rejects both reads and writes.

`$HOME` is always writable and needs no setup. When a command has to write outside it, the agent attaches `write_paths` to that one call; you get a prompt asking for your system password, and only after you approve are those paths bound in as well.

### MCP client configuration

MCP client and server live in `internal/runtime/mcp` and use the official [`modelcontextprotocol/go-sdk`](https://github.com/modelcontextprotocol/go-sdk). Configure stdio or streamable HTTP MCP servers in `~/.config/agenvoy/mcp.json`. Clients subscribe to tool-list change notifications and also poll every 60 seconds (30-second timeout per poll), re-registering tools when a remote server updates its catalog; an `Authorization` value in `headers` without a scheme gets `Bearer ` prepended; server instructions are surfaced into the agent system prompt. A server entry also accepts `env` (stdio), `auth: "oauth"` and `oauth_client_name` (HTTP); `${VAR}` is expanded in `args`, `env` and `headers`.

```json
{
  "servers": {
    "local-tools": {
      "command": "node",
      "args": ["/absolute/path/server.js"]
    },
    "remote-tools": {
      "url": "http://127.0.0.1:8000/mcp",
      "headers": { "Authorization": "Bearer ${MCP_TOKEN}" }
    }
  }
}
```

Agenvoy itself speaks MCP over stdio: run the `agen` binary with stdin piped (no TTY) and it starts the MCP server instead of the TUI. Register it in another agent by hand — Claude Code (`~/.claude.json`), OpenCode (`~/.config/opencode/opencode.jsonc`) and Codex (`~/.codex/config.toml`) each keep their own file:

```json
{
  "mcpServers": {
    "agenvoy": { "command": "agen" }
  }
}
```

```toml
[mcp_servers.agenvoy]
command = "agen"
```

### Session Classification

The TUI `/session` selector groups sessions by ID prefix: `cli-` for local CLI, `tg-` for Telegram, `dc-` for Discord, and `chat-` for Web/API; `temp-` sessions (short-lived work) are not listed. When at least two groups are detected, the selector shows an `all` tab and one tab per prefix, with the current session listed first. The daemon watches newly created session directories with `fsnotify` and writes the session ID and configured name to the daemon log.

Session personas are stored in the history SQLite database. `self_id` is normalized to lowercase and accepts only up to 32 ASCII letters, digits, `_`, or `-`; non-empty values must be unique. Legacy per-session files such as `bot.json` and `status.json` are no longer migrated automatically since v1.1.2.

## Usage

### Interactive TUI

```bash
agen
```

Type a message to run it in the current session. Everything else is a slash command; `/` alone opens a picker that also lists installed skills and scheduler entries.

| Command                    | Purpose                                                                                                                                                                                                                                                                                                                                                                   |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/model`                   | Eight tabs, one per routing role: **model** picks the session model (`auto` or a registered model; `d` removes the highlighted model, `t` sets its tier, `w` / `s` move it up / down to change the fallback order, saved on Enter) and `add`s a provider (`o` opens the provider console), **reasoning** picks the session level (`auto` or a fixed one), **dispatch** picks the routing model or `Decision Model`, **summary** picks the summary model (`auto` clears it), **decision** picks the decision model (`disable` turns it off), and **image** / **stt** / **tts** pick the model or provider for that role (`disable` clears it). `/model <tab>` or `/model add` opens that screen directly                                                                                                                                 |
| `/mcp`                     | List MCP servers (`d` removes one) and `add` new ones; per server: log in, set the OAuth client, pick always-allowed `tools` (first row `all`), reconnect                                                                                                                                                                                                                 |

Inside a popup, `esc` returns to the page that opened it and closes only the first page; list-only popups such as `/usage` scroll instead of selecting.

While a run is in progress, `esc` cancels it at once if it has not produced output yet; otherwise it asks **No**, **Yes cancel** or **Pause keep pending**. Cancelling — also `ctrl+c`, **Abort task** or `esc` in a confirmation or `ask_user` popup, and `POST /v1/session/:id/cancel/:task_hash` — discards the task's pending entry. Pausing, and any other interruption such as a timeout or a closed window, stops the run but keeps the entry so `/pending` can resume it. While a run is in progress only plain text can be sent, as steer; `/` commands are neither listed nor sent. Outside a popup `esc` first closes the `/` command picker, then the notice box, then cancels the run, then clears the input. While the status line shows `Connecting`, plain messages, Skills, `/pending` and cron dispatch are held; local `/` commands still work.

### Managing the daemon

```bash
agen stop
agen update
```

Running `agen` starts the local daemon when it is not already running.

### Web and file-response rendering

The backend preserves `[SEND_FILE:...]` markers while events move through result, SSE, pending, and multilog handlers so delivery metadata remains available to channel consumers. The web dashboard removes those markers only when rendering message text; users see the response body without the internal transport marker.

The web chat renders replies as rich markdown: ```` ```chartjs ```` blocks become charts (bar, line, pie, doughnut, radar, polarArea, scatter, bubble), ```` ```mermaid ```` blocks become diagrams (flowchart, sequenceDiagram, stateDiagram-v2, classDiagram, erDiagram, gantt, timeline), ```` ```math ```` blocks and inline `$...$` render as KaTeX, and other code blocks are syntax-highlighted. A block that fails to parse shows its source instead. Telegram and Discord receive plain markdown only.

### Local HTTP API

The daemon listens on `127.0.0.1:17989` and `[::1]:17989`. The port is fixed and not configurable.

```bash
curl --fail-with-body -sS \
  -H 'Content-Type: application/json' \
  -d '{"content":"List the available tools","persist":false}' \
  http://127.0.0.1:17989/v1/send
```

`/v1/chat/completions` is OpenAI-compatible and stateless: include prior messages in every request when continuity is needed. `reasoning_effort` accepts `none` `low` `medium` `high` `xhigh` `max` (plus the aliases `minimal` `extra` `ultra`); omitted or unrecognized values use the session level, or the selector's level when that is `auto`, otherwise `medium`.

### MCP server mode

When stdin is not a terminal, `agen` serves newline-delimited JSON-RPC over stdin/stdout:

```bash
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list","params":{}}' \
  | agen
```

Supported methods: `initialize`, `notifications/initialized`, `notifications/cancelled`, `tools/list`, `tools/call` and `ping`.

**Automation**

| Method         | Path                  | Description                                                                                                                                                                                                                                                                                                |
| -------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET`          | `/v1/schedule`        | **local** — list cron entries and one-off tasks as one `schedules` array, each tagged `type=cron\|task`; `?type=` narrows to one.                                                                                                                                                                          |
| `GET`          | `/v1/schedule/*skill` | **local** — read a scheduler skill as `name` / `body` (raw SKILL.md, frontmatter included) / `files` (the other files in its folder).                                                                                                                                                                      |
| `POST` `PATCH` | `/v1/schedule`        | **local** — create/update a scheduler skill from `name` / `content` (`content` carrying its own frontmatter is written as-is, otherwise the frontmatter is composed server-side) and rebind its whole entry set to `type=cron\|task`; switching type drops the entries the skill held under the other one. |
| `DELETE`       | `/v1/schedule`        | **local** — delete a skill's entries (`type` narrows to one, omitted removes both); trashes the skill when nothing else binds it.                                                                                                                                                                          |
| `POST`         | `/v1/schedule/run`    | **local** — fire a schedule now (`202 Accepted`).                                                                                                                                                                                                                                                          |

Create and update take `{type, name, content, expressions[], session_id?}`: `name` must match `[A-Za-z0-9_-]{1,64}`; `expressions` holds cron strings for `type=cron` and future points in time for `type=task`. `POST` returns 409 on a duplicate name and `PATCH` 404 when it is not found; `DELETE` takes `{skill, type?}` and returns 404 when no entry was removed, otherwise `{removed, trashed}`; `run` takes `{session_id, skill}`.

| ------------ | --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `GET` `POST` | `/v1/allowlist` | **local** — both allowlists in one object, `skill` and `tool`. `GET` reads `?scope=global\|project` (with `?work_dir=` required for `project`) for the skill block and `?prefix=` to narrow the tool block. `POST` takes `{skill: {name, scope?, work_dir?}}` to toggle one skill and/or `{tool: {prefix, entries}}` to replace just that prefix's auto-approve entries (same call the TUI's `/mcp` → tools makes), so unrelated rules survive; every entry must start with `prefix`, and `prefix*` collapses the rest. **Configuration**

| Method       | Path                    | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------ | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET` `POST` | `/v1/config/startup`    | **local** — read/set launch-on-login. `POST` `{enable}` writes or removes the launchd agent (macOS) or systemd user unit (Linux); it never starts or stops the running daemon, and takes effect at the next login. Both verbs answer with `enabled` (the setting, recorded under `startup` in `config.json` whenever it is changed) and `installed` (whether the unit file is actually on disk right now) — they disagree when the unit was removed outside Agenvoy.                                                                                                                                                                                                                                                                |

| `GET`        | `/v1/config/reply_lang` | **local** — read-only view of the configured reply language, shaped for a prompt. | `GET` `POST` | `/v1/config/output_dir` | **local** — read/set `output_dir`. `GET` returns `{output_dir, resolved}`, `resolved` being the directory actually in use. `POST` `{output_dir}` expands `~`, creates the directory, writes `config.json` and applies it to the running daemon at once, answering `{ok, output_dir, resolved}`; an empty string restores the default, and a path that cannot be created returns 400.                                                                                                                                                                                                                                                                                                                                                |

| `GET` `POST` | `/v1/config/skill_source` | **local** — read/set the external skill sources. `GET` returns `{sources, disabled}`; `POST` `{disabled:[...]}`; an unknown source returns 400, and skills are rescanned after saving. |

28 tools are always available (`run_tool`, used internally, included); six more are registered or excluded from a run depending on their prerequisite. Tools that cover several related actions take a `mode` argument rather than splitting into separate names.

Tools are sorted by name, and the tool payload carries only three full schemas — `find_tools`, `run_tool` and `reasoning_guide`; every other tool is listed by name only in the TurnContext injected each turn. The model fetches a schema with `find_tools` (returned as tool output rather than written back into the tool payload), then calls the tool through `run_tool(name, args)`. A call made before fetching the schema gets the schema back automatically with a request to call again, and calling any tool other than these three directly by name is rejected. The serialized tool block therefore stays byte-identical for the whole session and the prompt cache survives. The `claude-code` provider does not use `run_tool`: it receives only the tool names plus the full `find_tools` schema, and calls a tool directly by name once it has the schema. The `edit_file` patch mode accepts only `{old_string, new_string}` targets (plus optional `replace_all`); `new_string` replaces `old_string`, and insertion is expressed by repeating `old_string` at the start of `new_string`. Every target is matched against the file as it is on disk before any of them apply, so their order does not matter; an `old_string` that matches more than once without `replace_all`, two targets covering the same lines, a target whose `old_string` appears inside an earlier target's `new_string`, or a batch that would empty a non-empty file rejects the whole batch without writing; a target whose `old_string` equals its `new_string` is skipped and noted in the result, and nothing is written when the content does not change.
